# FASDELY — QA, Testing & Launch Readiness

Дата: 2026-08-31
Статус: рабочий документ

## Как читать этот документ

Промпт описывает сквозной путь гостя/персонала/админа — но пока существует
только Backend Foundation, тестировать интерфейсы нечего: гостевого
Mini App, интерфейса персонала и Admin Dashboard ещё не существует
(под-проекты 2–4). Этот документ разделяет: что из требований промпта
**уже реально протестировано на бэкенде** (с конкретными доказательствами,
не «наверное работает»), и что **станет тестируемым только после** появления
соответствующего под-проекта — это не забытая работа, а работа, для которой
пока нет объекта тестирования.

## Что уже протестировано (раздел 2 и 11 промпта — применимая к бэкенду часть)

Не по «выглядит правильным», а через реальные проверки на живой базе с
переключением ролей и специально «нечестными» сценариями:

| Проверка из промпта | Статус | Как проверено |
|---|---|---|
| Мультитенантная изоляция (бизнес A не видит бизнес B) | ✅ | Переключение роли на живой БД для 15+ таблиц; отдельно перепроверено после того, как нашли и закрыли дыру с самоназначением роли администратора |
| Изоляция по локациям | ✅ | Сотрудник локации A не видит заказы локации B — переключение роли на живых данных |
| Манипуляция ролью с фронтенда | ✅ | RLS проверяет роль на сервере через `auth_role()`, не доверяет ничему из запроса |
| IDOR (подмена ID заказа/товара/бизнеса) | ✅ | `create-order` проверяет принадлежность товара/модификатора нужному бизнесу; закрыта дыра с чужим модификатором |
| Манипуляция ценой с клиента | ✅ | Цена всегда пересчитывается на сервере, клиентская цена никогда не используется |
| Несанкционированная отмена заказа | ✅ | Проверка владения заказом раньше проверки статуса (чтобы не раскрыть статус чужого заказа через текст ошибки) |
| Двойной заказ (двойное нажатие) | ✅ | Ключ идемпотентности, привязанный к конкретному гостю |
| Гонка: два сотрудника одновременно принимают заказ | ✅ | Условное обновление в БД — второй запрос получает явный ответ «уже обработано», не тихий сбой |
| Товар/категория уходят в стоп-лист, пока в корзине | ✅ | Перепроверяется на сервере при `create-order`, а не только при показе меню |
| Просроченный неподтверждённый заказ | ✅ | Автоматическая задача (pg_cron) каждую минуту, проверено вызовом напрямую |

## Приоритет багов (раздел 15 промпта)

Классификация принята без изменений — уже применялась де-факто при
финальном ревью бэкенда:

- **CRITICAL** — утечка данных, несанкционированный доступ, сломанный
  заказ, дублирующиеся заказы. Пример из уже сделанного: самоназначение
  роли администратора при регистрации — это была бы CRITICAL-находка,
  если бы дошла до реального запуска.
- **HIGH** — серьёзный сбой в потоке заказа/персонала.
- **MEDIUM** — важная проблема с обходным путём.
- **LOW** — косметика.

Принцип «никогда не отгружать CRITICAL» соблюдается — именно поэтому
финальная проверка бэкенда включала полноценный цикл фикса и повторной
проверки найденной уязвимости, а не просто пометку «известная проблема».
