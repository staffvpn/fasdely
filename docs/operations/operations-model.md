# FASDELY — Операционная модель

Дата: 2026-08-31
Статус: рабочий документ

## Важно: этот документ обновлён под гибридное решение от 2026-08-30

Исходный операционный промпт описывает модель «владелец кафе присылает
абсолютно любое изменение через Telegram, оператор FASDELY вносит вручную».
Мы уже приняли отступление от этого (см.
`docs/superpowers/specs/2026-08-30-backend-foundation-design.md`, раздел
«Decision (2026-08-30): hybrid self-serve»): **владелец/сотрудник кафе
смогут сами через того же Telegram-бота включать/выключать позицию в
стоп-листе и менять цену уже существующего товара — без участия оператора
FASDELY.** Причина: это самые частые и при этом самые безопасные операции
(не портят карточку товара, не требуют контроля качества), и заставлять
писать оператору «убери чизкейк, он закончился» — реальное раздражающее
трение для занятого бариста.

**Всё остальное** (новая позиция, фото, описание, категории, сезонные
коллекции, акции) — по-прежнему через запрос оператору, как и было
задумано изначально. Это сохраняет главное отличие FASDELY от обычного
конструктора меню — контроль качества карточек товаров и цена, оправданную
управляемым сервисом, а не софтом.

Ниже — операционная модель промпта, адаптированная под это разделение.

## 1. Основной операционный принцип (обновлено)

Кафе:
- предоставляет информацию о новых позициях/фото/описаниях;
- **самостоятельно** переключает стоп-лист и меняет цену существующих
  позиций через бота;
- присылает запросы на всё остальное;
- получает и обрабатывает заказы.

FASDELY:
- создаёт новые позиции меню, категории, структуру;
- ведёт фото, описания, состав, КБЖУ, аллергены;
- управляет сезонными коллекциями и акциями;
- поддерживает кафе.

Поэтому нагрузка на оператора по-прежнему ключевая метрика бизнеса — но
она ниже, чем в исходной модели, ровно на объём стоп-листа/цен, которые
теперь не требуют участия человека со стороны FASDELY.

## 2. Онбординг клиента

Без изменений от исходного промпта — это по-прежнему полностью управляемый
процесс, стоп-лист/цена самообслуживания не отменяют необходимость
создать первое меню:

1. Создать бизнес.
2. Создать локацию.
3. Собрать брендинг.
4. Собрать меню.
5. Структурировать категории.
6. Добавить товары.
7. Добавить модификаторы.
8. Добавить фото.
9. Настроить часы работы.
10. Настроить доступность.
11. Протестировать оформление заказа.
12. Протестировать интерфейс персонала.
13. Настроить QR-назначение.
14. Выдать QR-материалы, если применимо.
15. Запуск.

Технически шаги 1–10 уже поддержаны схемой БД (Backend Foundation), но
UI для их выполнения (Admin Dashboard) — под-проект 4, ещё не построен.
Сейчас эти операции пришлось бы делать через прямые SQL-запросы — так
запускать реальных клиентов нельзя, только тестовые данные.

## 3–4. Обработка запросов через Telegram (сужено)

Актуально теперь **только для того, что не входит в самообслуживание**:
новая позиция, фото, описание, категория, акция, сезонная коллекция,
перенос между категориями и т.п.

Примеры запросов, которые больше НЕ должны идти в очередь оператора
(решаются самим кафе через бота):

- ~~«Поставь капучино на 320 ₽»~~ → теперь самообслуживание.
- ~~«Останови чизкейк, закончился»~~ → теперь самообслуживание.

Примеры, которые остаются запросами оператору:

- «Добавь новый фисташковый раф, вот фото» — новая позиция.
- «Создай летнюю коллекцию» — сезонная коллекция.
- «На Арбате прекращаем продавать круассаны насовсем» — если это не
  временная остановка, а решение исключить позицию из локационного
  меню, это структурное изменение, не тумблер стоп-листа.

## 5. Приоритет запросов

Без изменений: срочные (неверная цена/локация — но теперь это как раз
то, что кафе может исправить само за секунды через самообслуживание,
так что категория «срочное» на практике теперь почти целиком относится
к операционным ошибкам, которые кафе не может исправить само: неверное
фото, неверный текст описания), обычные, плановые.

## 6. Внутренняя очередь заявок

🔜 Не реализовано — часть будущей Admin Dashboard (под-проект 4). Модель
из промпта (бизнес, локация, текст запроса, приоритет, статус,
исполнитель, время создания/завершения, заметки; статусы NEW / IN
PROGRESS / WAITING FOR CUSTOMER / COMPLETED / CANCELLED) принимается как
целевая спецификация для этого под-проекта без изменений — она не
конфликтует с гибридным решением, просто теперь через неё проходит
меньше запросов.

## 7. Контроль качества

Частично уже реализовано автоматически: `menu_quality_by_business`
(`supabase/migrations/0007_menu_quality.sql`) считает долю опубликованных
товаров с заполненными фото/описанием/КБЖУ/аллергенами/ценой — это именно
тот контроль качества, который промпт просит делать вручную «перед
публикацией», только теперь он виден оператору как метрика, а не как
ручной чеклист на каждую позицию.

## 8. История изменений меню

✅ Уже реализовано автоматически (`audit_log`, триггеры на 6 таблицах,
включая цену/доступность локации — добавлено на финальном ревью
безопасности). Кто изменил, что изменил, когда — фиксируется без участия
разработчика в каждой отдельной операции. Это касается и изменений,
сделанных теперь самим кафе через самообслуживание — они тоже попадут в
`audit_log` с пометкой, что действие совершил `staff`/`business_owner`,
а не оператор FASDELY (это будет частью реализации под-проекта 2).

## 9. Поддержка

Без изменений от промпта: каналы — Telegram/email/внутренняя система;
категории — Меню, Заказы, Персонал, Аккаунт, Подписка, Техническая
проблема, QR, Другое.

## 10. Управление инцидентами

Без изменений — процесс (выявить → локализовать → сообщить → исправить →
проверить → задокументировать) станет актуален с реальным трафиком.

## 11–12. Мультилокационность, мастер-меню

✅ Уже реализовано на уровне схемы БД: `product_location_overrides`
(таблица из Backend Foundation) — это ровно модель «мастер-значение +
переопределение на локации» из промпта. Товар создаётся один раз на
уровне бизнеса, каждая локация может переопределить цену/доступность.
Если мастер-цена меняется, а у локации нет собственного переопределения —
она автоматически наследует новое значение (просто потому что
переопределения не существует в таблице, а не потому что это отдельно
запрограммировано).

## 13. Массовые операции

🔜 Не реализовано — требует Admin Dashboard (под-проект 4). Схема БД уже
это поддерживает (можно менять цену у многих товаров одним SQL-запросом
уже сейчас), но интерфейса для оператора нет.

## 14. Нагрузка на оператора

🔜 Метрики (заявок в день, среднее время обработки и т.д.) станут
измеримыми только когда появится очередь заявок из раздела 6. Пока не с
чего собирать статистику — реальных клиентов ещё нет.

## 15. Дорожная карта автоматизации

Принимается без изменений — уже согласуется с принципом «без ИИ в MVP» из
исходного продуктового промпта. Этап 1 (шаблоны, массовое редактирование)
логично совпадает с под-проектом 4.

## 16–17. Customer success, отток

🔜 Не применимо, пока нет реальных клиентов. Сигналы (заказы, активные
дни, обновления меню) технически уже собираемы из существующих таблиц
(`orders`, `audit_log`) — считать их можно будет, как только появится
первый настоящий клиент.

## 18. Лимиты добросовестного использования

✅ Уже определены как коммерческая политика в
`docs/business/monetization.md` (позиций в меню, запросов на изменение в
месяц — по тарифам). Технически лимиты пока не проверяются кодом
(например, никто не блокирует 41-й запрос при лимите 40) — это тоже
задача Admin Dashboard.

## 19. Будущая команда

Без изменений — не нанимать раньше, чем оправдано нагрузкой. Ролевая
модель RLS уже готова добавить более гранулярные роли (см.
`docs/security/security-privacy-legal.md`, раздел 1–4), когда это
реально понадобится.

## 20–24. Масштабируемость, SOP, экономика поддержки, риски

Без изменений от исходного промпта — это качественные принципы, а не
задачи с чёткими артефактами. Главный операционный риск («ручная нагрузка
растёт быстрее выручки») снижен гибридным решением ровно в объёме
стоп-листа/цены — это была осознанная причина принять гибрид, а не просто
удобство для пользователя интерфейса.
